This page is the release-level upgrade reference. The step-by-step procedure — drain, stop, snapshot, migrate,
provision, start, and the digest-based rollback — is on the
[v1-single-node profile page](/docs/deployment/v1-single-node#upgrade-and-rollback). This page adds what that procedure
depends on: how many migrations you are applying, which ones cannot be undone, what must exist before you start, and
what a rollback cannot recover.

## Versions and migrations

The reference upgrade is `v0.1.9` → current `main` head. Both counts below are `.up.sql` files under
`infra/migrations/postgres/`; the migration runner applies them in order.

| Point | PostgreSQL migrations | ClickHouse migrations |
| --- | --- | --- |
| `v0.1.9` | 39 | 5 |
| `6f12c96c` (2026-11-10) | 58 | 6 |
| current `main` head | 71 | 6 |

An upgrade from `v0.1.9` therefore applies 32 PostgreSQL migrations and one ClickHouse migration. The counts are a
property of the checkout you build from, not of the tag you are leaving: the `migrate` one-shot is built from the
target checkout, so build and migrate from the same commit.

## Precondition: a snapshot and a restore you have run

The upgrade and the rollback both rest on one database snapshot, so the snapshot is not optional and neither is the
proof that it restores.

- Take the snapshot after draining and stopping, as the profile page's procedure states.
- Rehearse the restore before the change window. `05.v1-single-node.md` requires both directions to be rehearsed from a
  real snapshot of the previous release, with the commands, image IDs, and row counts recorded.
- Keep the window between snapshot and rollback short, and keep token revocations, deletion requests, and legal-hold
  records outside the database so they can be re-applied.

The supported command surface is smaller than this precondition implies. There is no `v1-backup` or `v1-restore` Make
target yet, and no restore runbook: `engineering/runbooks/RUNBOOKS.md` covers proxy, auth, Redis, PostgreSQL,
ClickHouse, worker, and isolation, but not restore itself. The committed drill is a `pg_dump` fallback whose report
records `rpo_pass: false`. Until those land, a restore from an off-host repository is an operator-built procedure, and
the precondition cannot be met by a supported command. See
[`RUNBOOKS.md`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/runbooks/RUNBOOKS.md).

## Irreversible migration families

Migrations are forward-only in production: starting an older image against the migrated schema is not a supported
rollback ([`DEPLOYMENT.md`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/DEPLOYMENT.md) §7.2). Two
families cannot be undone by a `down` migration even in development:

1. **Memory lifecycle (`000045_memory_lifecycle`).** The down migration is safe only before lifecycle events have been
   consumed or used as authority. Once published, lifecycle history is not reconstructible
   (`infra/migrations/postgres/000045_memory_lifecycle.down.sql`:1-3). A rollback after a consumer has acted on outbox
   rows needs an explicit recovery plan, not the down file.
2. **ClickHouse analytics migrations (`infra/migrations/clickhouse/`).** ClickHouse has no transactional rollback for
   most DDL, and the down files drop the tables they created. Applying a destructive `up`, or running a `down` against a
   live database, destroys analytics rows with no recovery path — which is why the migration suite gates destructive
   DDL before it can be applied (`infra/migrations/clickhouse/destructive_ddl_unit_test.go`:11-13).

Both families make the snapshot the only recovery path. Neither is repaired by re-running a migration.

## Rollback limits

Rollback restores the snapshot and starts the previous image digests; it is not a schema downgrade. The limits that
matter:

- **Forward-only schema.** An older image against the migrated schema is unsupported. The rollback unit is the
  snapshot, not the `down` file.
- **Stop the stack; do not rebuild.** A rebuild replaces the images you are trying to recover. Retag each recorded
  image ID onto its Compose name and start with `--no-build`.
- **Transient Redis state is lost.** Reset the extraction queue, the result backend, and the caches; re-submit
  extraction work accepted after the snapshot.
- **Database state moves back in time.** Re-apply token and PAT revocations, user suspensions, accepted deletion
  requests, legal-hold creations and clearances, and completed forgets, in that order, before reopening traffic. The
  profile page lists the full sequence.
- **Capability-login verifiers revert.** They live in `pg_authid`. The recreated one-shots rewrite them from the
  current `.env`, so a credential rotated after the snapshot must still be in `.env` when the stack starts.

A rollback that has never been executed is not evidence. Rehearse both directions and record both.

## Support window

**No version support window or support matrix is signed.** What is true today:

- There is exactly one supported deployment profile, `v1-single-node`, selected by
  [ADR-0097](https://github.com/Rick1330/ibex-harness/blob/main/engineering/adr/0097-v1-supported-profile.md). Kubernetes,
  Helm, and HA topologies are outside it.
- There is no hosted offering and no hosted support claim.
- No document states how long a released version receives fixes, or which version-to-version skips are supported. The
  only recorded upgrade path is the `v0.1.9` → head rehearsal this page describes; no other skip has been rehearsed.

A support window and support matrix are therefore an **open owner decision**, not a policy this page can state. The
remaining v1 gaps record the item as `P1-46` in
[`35-v1-remaining-gaps-staged-2026-11-13.md`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/architecture-v2/35-v1-remaining-gaps-staged-2026-11-13.md)
§3, and the open owner questions are §9 of the same document. Until the owner signs a window, treat every release as
supported only at the version you are running, upgrade one rehearsal at a time, and do not promise a customer a
maintenance or upgrade window from this page.
