`POST /v1/responses` exposes a bounded Responses API contract. It is a separate route with its own parser and capability gate; it is not a chat-completions alias or a default-mock path.

## Required headers

| Header | Required | Notes |
| --- | --- | --- |
| `Authorization: Bearer <pat>` | Yes | Must carry `ProxyChatCompletion` |
| `X-IBEX-Agent-ID` | Yes | Active agent in the token organization |
| `Content-Type: application/json` | Yes | JSON only |

## Admission and capability checks

The route runs:

```text
body limit → content type → auth → agent verify → policy mutation → rate limit → budget
→ parse Responses → provider routing → capability gate → provider dispatch
```

The capability gate rejects a request when:

- The provider/model is unknown or has no verified manifest entry.
- A requested capability is not verified for that model.
- `stream=true` is requested.

The route requires a registered provider that implements the Responses surface, a current verified capability-manifest
entry, provider credentials, and the usage writer configured by `CLICKHOUSE_DSN`. The default mock provider is sufficient
for Chat Completions smoke tests but is not a Responses-capable provider. If the required credential resolver or usage
writer is missing at admission, the route fails closed with `503 SERVICE_DEGRADED`. If the credential resolver returns
an error while resolving the tenant credential, the route returns `503 AUTH_UNAVAILABLE` instead.

`stream=true` is currently rejected because streaming Responses is not implemented. Use `/v1/chat/completions` for streaming.

## Errors

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | The Responses body could not be parsed |
| 501 | `PROVIDER_NOT_CONFIGURED` | No provider is registered for the requested model |
| 422 | `CAPABILITY_UNSUPPORTED` | The provider/model cannot perform the requested operation, including streaming |
| 503 | `CAPABILITY_UNKNOWN` | A registered provider/model lacks current verified capability evidence |
| 503 | `SERVICE_DEGRADED` | A required credential resolver or usage writer is missing at admission |
| 503 | `AUTH_UNAVAILABLE` | The credential resolver returned an error while resolving the tenant credential |
| 502 | `PROVIDER_UNAVAILABLE` | The upstream Responses call failed |
| 429 | `RATE_LIMITED` | Org or upstream limit |
| 402 | `BUDGET_EXCEEDED` | Hard-cap admission denied |
| 503 | `BUDGET_UNAVAILABLE` | Admission hold could not be reserved |

All errors use the [stable envelope](/docs/api-reference/errors).

## Usage accounting

Successful responses with complete usage are enqueued as usage facts through the billing writer. If usage is missing,
incomplete, overflows the billing limits, or the usage enqueue fails, the provider response is still returned with
`200 OK` and `X-IBEX-Usage-Accounting: pending`; the condition is logged and marked pending rather than silently
treated as zero. These post-success accounting failures do not become retryable `503` responses. A missing usage
writer is different: it is an admission dependency and returns `503 SERVICE_DEGRADED` before provider dispatch.

| Response header | Meaning |
| --- | --- |
| `X-IBEX-Usage-Accounting: pending` | The upstream response succeeded, but usage was missing/incomplete or could not be enqueued; the response remains `200 OK`. |

::callout

{"type":"warning","title":"Accounting is not billing-grade"}

## Example

```bash
curl -s -w "\nHTTP %{http_code}\n" \
  -X POST http://localhost:8080/v1/responses \
  -H "Authorization: Bearer ${IBEX_DEV_TOKEN}" \
  -H "X-IBEX-Agent-ID: ${IBEX_DEV_AGENT_ID}" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o","input":"hello"}'
```

This request succeeds only when the selected provider is Responses-capable and its current capability manifest entry,
credentials, and usage writer are available. Missing admission dependencies return the errors above; a credential
resolver error returns `AUTH_UNAVAILABLE`. A post-success usage enqueue failure preserves `200 OK` and sets
`X-IBEX-Usage-Accounting: pending`. A model with no registered provider returns `501 PROVIDER_NOT_CONFIGURED`; a
registered provider/model with missing, stale, unsupported, or unverified capability evidence is rejected by the
capability gate and is not silently replaced by the default mock provider.

## Limits

- No streaming.
- No guarantee that every provider exposes every Responses field.
- Chat and Responses have separate semantics even when they share admission middleware.
- A mount is not a hosted availability guarantee.
