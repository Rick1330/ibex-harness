“OpenAI-compatible” is not one contract. Chat Completions, Responses, native provider APIs, MCP, and framework integrations have different shapes and different support boundaries. This page records the policy; it is not a certification matrix for every client version.

## Supported surfaces

| Surface | Current support | Important boundary |
| --- | --- | --- |
| Chat Completions | OpenAI-compatible `POST /v1/chat/completions`; streaming and non-streaming | Tools, structured output, and provider-specific fields depend on the selected adapter and model manifest |
| Responses | Non-streaming subset at `POST /v1/responses` | Separate typed contract; semantic SSE, replay persistence, and multi-call execution are not shipped |
| Anthropic | Chat Completions-facing adapter that calls native Messages | Text-oriented exposed surface; Anthropic tools, vision, JSON schema, and reasoning are not advertised unless the adapter is extended |
| OpenAI | Chat Completions plus a separate Responses slice | A model ID is not a capability contract; extras require allowlisting and overlays |
| Self-hosted OpenAI-compatible | Chat Completions via a configured `/v1` backend | Provider availability and model behavior are environment-specific |
| MCP memory | Streamable HTTP; search, write, feedback | Not an OAuth authorization server; no per-agent rate-limit claim |
| MCP operator | Streamable HTTP; four read-only metadata tools | Default-off; stdio not implemented; PolicySnapshot evaluation not wired |
| Management HTTP | `/v1` tenant and operator routes | Mounted routes are not hosted operator readiness |
| Auth gRPC | Internal `AuthService` | `ValidateToken` is private-network only; no public REST token API |
| SDKs, CLIs, framework integrations | No general support claim | A repository integration is not support evidence |

Hosted Claude Code, Codex, Cursor, Copilot, or other tools that connect directly to a provider without IBEX are outside IBEX's governance. IBEX cannot enforce policy, capture evidence, or claim compatibility for a path that bypasses it.

## Version axes

These move independently and should be recorded together in evidence:

- Contract major version
- Protobuf package and service version
- REST `/v1`
- MCP protocol and tool-schema version
- Provider adapter version
- Model deployment identity
- Tokenizer family and asset version
- Event schema version
- Database migration version
- SDK/CLI version
- Feature flags and deployment profile

A model alias such as `fast` must resolve to an immutable deployment identity before execution. A mutable provider catalog entry is not a stable contract.

## Compatibility rules

- REST remains `/v1` until a deliberate major version.
- Additive changes still need examples, generated artifacts, and tests.
- Protobuf field numbers and names are never reused; removed fields are reserved.
- MCP tool IDs, schemas, and result shapes are versioned and hashable.
- Database changes use expand → dual-read/write → backfill → verify → contract.
- Embedding or tokenizer profile changes are versioned migrations, never silent index replacement.
- Mixed-version behavior must be tested when old and new services can overlap during rollout.

## The v1.0 support profile

The **supported profile** for v1.0 is `v1-single-node`: single-node, self-hosted Docker Compose with the component pins
and transport contract in
[ADR-0097](https://github.com/Rick1330/ibex-harness/blob/main/engineering/adr/0097-v1-supported-profile.md). It ships as
one Compose project behind an edge TLS terminator; see [v1-single-node profile](/docs/deployment/v1-single-node).
Kubernetes/Helm and HA topologies, hosted or measured SLOs, and the other exclusions recorded in the ADR remain outside
the 1.0 scope. A local start is not a hosted, HA, multi-user, or measured-SLO claim.

Upgrade is a stop-the-stack operation: stop the stack, snapshot the database, run the one-shot migration service, and
start the new images by digest. Rollback is also a stop-the-stack operation: stop the stack, restore the snapshot, and
start the previous images by digest. Migrations are forward-only, so starting the previous digests against a migrated
schema is not a supported rollback, and a release note must not imply that it is.

The deprecation window is selected: **180 days** between notice and removal for a `stable` contract, and **31 days** for
a `beta` contract. The same window applies to all three surfaces — REST routes, gRPC methods, and MCP tool schemas.
REST deprecations are announced on the wire with the standard `Deprecation`, `Sunset`, and `Link` headers; gRPC methods
and MCP tools have no standard deprecation header, so the committed record is the notice of record.

**Nothing is deprecated today.** The committed record
[`contracts/deprecations.json`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/architecture-v2/contracts/deprecations.json)
ships with an empty `entries` array, so no consumer needs to act. The windows, header names, and record shape are the
policy of record in
[`16-compatibility-and-versioning.md`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/architecture-v2/16-compatibility-and-versioning.md);
do not invent a date that is not recorded there.

## Breaking changes

A breaking change requires:

1. An ADR describing the boundary and tradeoff.
2. A migration or compatibility shim.
3. A deprecation notice and support window.
4. Compatibility fixtures and mixed-version tests.
5. A rollback or roll-forward plan.
6. An update to the current-state and status documentation.

The public windows are **180 days** for `stable` contracts and **31 days** for `beta` contracts, covering REST routes,
gRPC methods, and MCP tool schemas. No contract is deprecated today and the record is empty. A date is real only when it
is recorded in
[`contracts/deprecations.json`](https://github.com/Rick1330/ibex-harness/blob/main/engineering/architecture-v2/contracts/deprecations.json);
do not invent one.

## Client certification

For each client or framework, a real support claim would record:

- Client and version
- Transport and endpoint
- Identity and configuration model
- Tested features
- Known limitations
- Diagnostics and error mapping
- Last verification date

No such per-client certification table is currently published. The absence is deliberate: a merged example, a green local test, or a provider's compatibility statement is not IBEX support evidence.

## What is not supported

- A promise that every OpenAI SDK feature works against Chat Completions.
- Lossless flattening of Responses into Chat Completions.
- Native Anthropic Messages as a public IBEX endpoint.
- Provider capabilities inferred from a model name alone.
- MCP stdio in production or a write-capable operator tool.
- Cross-tenant compatibility shortcuts, project-scoped URLs, or a `projects` entity.
- A hosted SLA or version-support matrix that is not in the contract registry.
