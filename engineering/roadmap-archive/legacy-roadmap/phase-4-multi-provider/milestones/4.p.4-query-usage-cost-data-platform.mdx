**Status:** In progress — ledger and hard-cap foundations exist; read and reconciliation contracts remain.
**Outcome:** Dashboard reads are bounded, explainable, tenant-scoped, and explicit about usage freshness and cost certainty.

<Callout type="note" title="Track D read contract">
  D2–D6 consume typed, server-bounded query responses. Each response includes the applied tenant/time scope, cursor, `truncated`, matched/returned counts, freshness/completeness, ingestion lag, sampling, retention boundary, and source/rate-card/policy versions. ## Query and lifecycle contract

The typed query grammar defines fields, operators, time ranges, facets, cursor pagination, query budgets, and saved-view serialization. High-cardinality IDs remain event fields rather than metric labels. Usage facts are immutable and tenant-scoped; billing retention is a documented carve-out from org deletion. Query errors, unavailable dependencies, and bounded truncation are visible states, not empty-success responses.

## Estimate versus actual contract

At enqueue, freeze `estimated_cost_cents` and `rate_card_version`. Only a provider invoice or other explicitly named authoritative source may produce `actual_cost_cents`; reconciliation must retain source, version, timestamp, currency, and adjustment lineage. Until that source exists, the UI and API must label estimates as advisory, omit or mark actuals unavailable, and expose estimate-to-actual drift as deferred—not silently equate estimates with actuals. Spend-cap decisions are a separate enforcement record and may fail closed even while reconciliation is pending.

## Residuals

The baseline records CH-to-Postgres spent rollup and hard-cap denial foundations. Invoice reconciliation, drift alerts, full saved-view round-trip, autocomplete, and the complete operator browser matrix remain open; issue #859 is the stated blocker for estimate-to-actual reconciliation. D2–D6 must preserve these labels.

## Verification gate

Run tenant-scoped query contract fixtures, EXPLAIN samples, duplicate/retry billing tests, rate-card replay, hard-cap denial, freshness/truncation checks, and estimate/actual separation tests. P6 must parse responses at runtime and prove cache isolation across users and tenants.

## Rollout and rollback

**Trigger:** query scope leak, hard-cap error, reconciliation drift, or SLO breach. **Reversal:** disable hard enforcement only through an approved alert-only control, preserve immutable facts and versions, and reconcile outstanding decisions before re-enabling.
