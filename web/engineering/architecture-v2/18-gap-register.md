### Finding — GAP-005/GAP-011 relay payload integrity and acknowledgement-loss evidence

- **Reproducible steps:** Construct or retrieve an outbox row whose `payload_digest` is a well-formed 64-character hexadecimal string for different bytes; or deliver a claimed row successfully and lose the `mark_delivered` acknowledgement before replaying it.

- **Actual:** The relay verifies digest equality and rejects unclassified/prohibited/unsupported classes, absent explicit fences, or sinks without the typed fence-aware hook. Typed permanent rejections go directly to poison. The class is producer-declared; relay validation does not inspect or sanitize payload contents.

- **Profile:** PostgreSQL evidence/outbox relay; local integration profile only. Hosted/HA profiles are not certified.
- **Evidence (verified 2026-10-08):** evidenceoutbox unit tests pass; all six PostgreSQL-backed evidenceoutbox integration tests pass against the local Podman test database, including outbox persistence, replay, tenant RLS, and role restrictions. ## DECISIONS NEEDED before the next implementation slice

1. **Production evidence producer metadata and relay readiness (P1).** The current session producer at `services/proxy/internal/http/session/evidence.go:91-118` sets neither `RedactionClass` nor `TombstoneFence`; the store therefore writes `unclassified` and no fence, and the relay intentionally poisons those rows before delivery. No reviewed sanitizer or authoritative resource-version source exists at that producer. **Options:** (A) retain fail-closed behavior and keep affected rows out of projection until a producer-specific sanitized schema and lifecycle fence are approved; (B) label current payloads `metadata` and infer a fence from request/run IDs; (C) relax relay validation for legacy rows. **Recommendation:** A. Do not infer safety or deletion authority; define and test producer-specific sanitization and authoritative resource identity before enabling a production relay.
2. **Memory historical-mode trust boundary.** Current user-facing repository code explicitly requests `USER_RETRIEVAL`, and the conflict loader rejects that mode; however, `SearchMode` remains an in-process `PgVectorStore.search` parameter, not a capability token, so a direct internal caller can explicitly request historical candidates. **Options:** (A) rely on audited call sites and prohibit user-controlled mode selection; (B) before broader use, expose historical search only through a dedicated write-path API/adapter and keep the general read API user-fenced; (C) expose mode selection to callers. **Recommendation:** B before expanding usage; C is rejected. Current tests establish the existing user-read path, not an unforgeable internal authorization boundary.
3. **PolicySnapshot authority identity and freshness.** The recommended candidate is an immutable AuthService-issued snapshot with ID, digest, effective epoch, and freshness window, but exact authority identity, freshness duration, and stale-state behavior remain owner decisions. **Options:** approve this candidate or name another authority and define its proof/expiry. **Recommendation:** approve the AuthService/enforcement-plane candidate with explicit freshness and stale-denial tests; do not add runtime policy propagation until recorded.
4. **HTTP mapping for evidence acknowledgement.** The semantics are fixed: normal success only after durable evidence/outbox commit; required-evidence failure or unknown commit never returns success; `uncertified` is typed and allowed only with durable retry/reconciliation state under an explicitly degraded profile. Exact HTTP/error codes are not chosen. **Options:** (A) candidate mapping: `503 evidence_unavailable` for failed/unknown required durability, and a profile-approved `202` response carrying `outcome=uncertified` only after retry state is durable; (B) select operation-specific codes while preserving those semantics. **Recommendation:** A as the default candidate, subject to owner approval and golden response tests; never retain silent log-and-continue.
