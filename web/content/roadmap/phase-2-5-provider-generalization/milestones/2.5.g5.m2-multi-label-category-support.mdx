## Why This Milestone Exists

The current single `category` enum column (`MemoryCategory`) cannot represent memories that legitimately span multiple categories — for example, "I always use dark mode because bright screens give me migraines" is both `preference` and `factual`. This milestone adds an additive join table so Phase 3's write pipeline is built against the right shape from day one, avoiding the "single mutually-exclusive enum" mistake.

---

## Non-Goals

- Application code depending on the new join table (pure schema-readiness, application use is Phase 3)
- Removing the existing `category` column (backward-compat default during transition)
- Changing the category taxonomy itself

## Working notes

Preferred starting points and open questions — situational, and expected to evolve with further research during implementation.

### Migration

```sql
CREATE TABLE ibex_core.memory_categories (
 memory_id UUID NOT NULL REFERENCES ibex_core.memories(id) ON DELETE CASCADE,
 category TEXT NOT NULL CHECK (category IN ('factual','preference','behavioral','episodic','procedural')),
 confidence NUMERIC(3,2) NOT NULL DEFAULT 1.00,
 PRIMARY KEY (memory_id, category)
);
```

### Key constraints

- The existing `category` column on `memories` is **kept** for backward compatibility — it serves as the default/primary category during the transition period.
- The join table is additive: a memory can have 1..N category labels, each with its own confidence score.
- `ON DELETE CASCADE` ensures GDPR deletion cascades correctly.
- RLS policy should be applied to the new table, matching the `memories` table's tenant isolation pattern.
