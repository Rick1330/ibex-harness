## Why This Milestone Exists

Today, supported models are effectively a hardcoded list, and `Registry.For(model)` only reports *which provider* handles a model, not *what that model can do*. With Anthropic and later self-hosted vLLM models that differ in context windows, tool-calling support, and vision support, provider identity alone is not enough for the proxy or future context-assembly engine (for example token-budget sizing, or whether a tool-call request is even valid).

## Non-Goals

- Dynamic capability negotiation at runtime (static table is correct for now)
- Pricing/cost data per model (separate concern)
- Per-request model selection logic (Phase 4 routing)

## Working notes

Preferred starting points and open questions — situational, and expected to evolve with further research during implementation.

### Where the data comes from

Three options, ranked as a starting point for planning:

1. **Maintain a small, curated table in-repo**, hand-verified against each vendor's docs (map literal or embedded JSON/YAML). For the ~10–20 models likely near term, this stays easy to review in a PR. Strongest default when auditability matters.

2. **Use LiteLLM's `model_prices_and_context_window.json` as a periodically-synced reference dataset**, not a live dependency. A small sync script can fetch that JSON, filter it to registered models, and regenerate the in-repo table. Useful as an upstream verification path rather than as the production source of truth.

3. **Take a runtime dependency on the file directly**. This is generally the weakest option for the near-term roadmap because it covers hundreds of unused models, adds re-parsing logic, and ties capability correctness to an external repo's update schedule. If this path is explored, it should be treated as follow-up investigation and implemented with versioned snapshots rather than a live runtime dependency.

If implementation constraints change, this ranking can be revisited. In particular, the LiteLLM-sync path is worth investigating if the model matrix grows faster than a hand-maintained table remains comfortable to review.

### Registry extension

The `Registry` type gains `Capability` alongside `For`:

```go
// Capability returns the capability record for the given model ID.
// Returns (ModelCapability{}, false) if no capability is registered for the model.
func (r *Registry) Capability(model string) (ModelCapability, bool)
```

Capabilities are registered at `NewRegistry` time, paired with the provider implementation. A model without a capability entry is a configuration error surfaced at startup, not at request time.

## Success signals

Outcome-oriented signals that the milestone is in good shape. Exact filenames, package layouts, and commands may differ from any sketches above.

- A capability record exists per registered model (context window, tools/vision/streaming, tokenizer family)
- Lookup by model ID is available alongside provider lookup
- OpenAI and Anthropic models used in Phase 2.5 have capability entries
- Missing capability is a startup/configuration error, not a silent nil at request time
- Optional: a sync/diff path against an upstream table if the curated table is kept small
- Tests cover lookup, missing-model failure, and tokenizer-family presence
- Repo guards / CI checks still pass
