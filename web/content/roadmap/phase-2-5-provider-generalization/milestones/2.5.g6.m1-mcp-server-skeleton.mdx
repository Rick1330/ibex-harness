## Why This Milestone Exists

Ship the MCP server now against stub/mock tool handlers (same `IBEX_LLM_MODE=mock` pattern already used for the LLM provider registry) so the auth boundary, OAuth flow, and audit-log wiring are proven and testable before Phase 3's real memory service exists to plug in behind it. This follows the "build the seam before the thing that uses it" logic used throughout Phase 2.5.

This is explicitly **not** a general tool-call broker — it's an MCP server that exposes exactly two IBEX capabilities as MCP tools, secured via OAuth at the server layer.

---

## Non-Goals

- Real memory read/write (stub handlers only — Phase 3.5 adds real implementations)
- General tool-call brokering
- Any MCP capability beyond `write_memory` and `search_memory` stubs

## Working notes

Preferred starting points and open questions — situational, and expected to evolve with further research during implementation.

### Why Python + official SDK

The MCP spec (JSON-RPC framing, capability negotiation, resource/tool schemas) is still evolving; hand-rolling it against a moving target is wasted, fragile effort. The official `mcp` Python SDK (Anthropic-maintained, open source, MIT-licensed) tracks spec changes automatically.

### Auth integration

OAuth resource-server validation reuses `AuthService.ValidateToken` via gRPC (same client the proxy already uses) rather than a second, parallel auth implementation — one identity system, two protocol surfaces (REST/proxy, MCP).

### Audit trail

Every tool invocation is written to the same ClickHouse trace pipeline the proxy already uses for LLM calls, so "audited enterprise remote action" is true from day one.
