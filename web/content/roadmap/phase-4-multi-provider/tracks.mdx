## Track P — Operator Readiness, Evidence & Control Plane

## Canonical dependency model

Use these graph terms everywhere: **P0**, **P1**, **D0**, **P6-bootstrap**, **P6-slice-certification**, **D1**, **D2**, **D3**, **D4**, **D5**, **D6**, **E1**, **E2**, **E3**, and **E4**. The acyclic dependency model is:

```text
P0 → P1
P0 + P1 → (D0 ∥ P6-bootstrap)
D0 + P0 + P1 + P6-bootstrap → D1
P2 + P6-slice-certification → D2
P3 + P6-slice-certification → D3
P3 + P6-slice-certification → D4
P1 + P2 + P4 + P6-slice-certification → D5
P4 + P6-slice-certification → D6
P6-bootstrap + D1 + D2 evidence → E1
resilience evidence → E2
E1 + E2 → E3
all P/D evidence + E1 + E2 + E3 + F4-035 disposition → E4
```

`P6-bootstrap` establishes the harness and manifest contract. `P6-slice-certification` is produced separately for each D slice after that slice's required P contract is available; it is not a claim that all assurance work is complete. `D0` and `P6-bootstrap` may proceed in parallel only after P0 and P1 are available. `E1` consumes P6-bootstrap plus D1/D2 evidence, `E2` consumes resilience evidence, `E3` follows E1 and E2, and E4 signs off all evidence and F4-035.

## Track D — Operator Capability Slices

**Purpose:** deliver the world-class operator product as independently verifiable, end-to-end capability slices.

**Sequencing:** `P0 + P1 → (D0 ∥ P6-bootstrap) → D1`; then each of D2–D6 requires its own P contract plus P6-slice-certification.

`D0` establishes `services/operator-web` as the canonical application boundary. `services/dashboard` remains compatibility-only during migration and is retired only after its cutover gate passes. D1 must use real context, Overview, platform-health, and SSE contracts; navigation is not live domain delivery, and org switching is a deferred gate until verified. D2 is metadata-first and remains evidence-gated by P2 plus P6-slice-certification. D3–D6 each consume their named P contract plus P6-slice-certification.
