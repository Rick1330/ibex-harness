# Phase 4 — Findings Register

<Callout type="note" title="How to read this register">
  These findings are roadmap constraints derived from repository inspection and product design review (see `web/engineering/research/operator-platform/`). They are not claims that a future contract is already implemented. Each finding is mapped to a milestone that must produce verification evidence before it can be closed. Engineering P0/P1 items may be closed by implementation or by an explicit residual-risk acceptance recorded on 4.E.4.
</Callout>

## Executive finding

The original Phase 4 plan was a minimal feature list. It described screens and endpoints but did not define the runtime, evidence graph, privacy lifecycle, tenant policy, query semantics, durable usage facts, recovery model, or executable release gates required for a world-class operator product. Staff-engineering audits further showed **authorization fail-open**, **incomplete cross-store deletion**, **trace join gaps**, and **assembly correctness defects** that would make a premature Track D UI dishonest. The redesign therefore places readiness and control-plane work before dashboard UI and treats each capability as a vertical slice with contract and assurance evidence.

## Closure rule

A finding is closed only when the referenced milestone has a merged implementation **or** an accepted residual-risk record, a reproducible verification artifact, an owner, and an operational rollback or residual-risk decision. A roadmap page alone is evidence of intent, not closure. **Zero open P0 findings** is mandatory for Phase 4 exit (4.E.4).
