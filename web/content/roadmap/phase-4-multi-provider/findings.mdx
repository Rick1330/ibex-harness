# Phase 4 — Findings Register

<Callout type="note" title="How to read this register">
Status vocabulary is limited to **planned/specification**, **mounted-but-provisional**, **implemented-with-evidence**, and **residual-risk**. These findings are roadmap constraints derived from repository inspection and product design review (see `web/engineering/research/operator-platform/` and `CONSOLE_DEEP_READINESS_PLAN.md`). They are not claims that a future contract is already implemented. Each finding is mapped to a milestone that must produce verification evidence before it can reach implemented-with-evidence or residual-risk. Engineering P0/P1 items may reach implemented-with-evidence only with implementation evidence, or residual-risk with an explicit acceptance recorded on 4.E.4.
</Callout>

## Executive finding

The original Phase 4 plan was a minimal feature list. It described screens and endpoints but did not define the runtime, evidence graph, privacy lifecycle, tenant policy, query semantics, durable usage facts, recovery model, or executable release gates required for a world-class operator product. Staff-engineering audits further showed **authorization fail-open**, **incomplete cross-store deletion**, **trace join gaps**, and **assembly correctness defects** that would make a premature Track D UI dishonest. The redesign therefore places readiness and control-plane work before dashboard UI and treats each capability as a vertical slice with contract and assurance evidence.

## Current fact versus proposed target

| Area | Current fact at the review baseline | Proposed target; not implementation evidence |
|---|---|---|
| Public web | `web/` is the public documentation, roadmap, benchmark, and marketing site. | Keep authenticated operator routes out of the public documentation application. |
| Dashboard surfaces | `services/dashboard/` is a small provisional 4.P.0 connection shell; the broader operator mock is a separate fixture-backed prototype. | Make `services/console/` the canonical operator application and keep `services/dashboard/` compatibility-only until a retirement gate passes. |
| D1 data path | The readiness review identified useful backend foundations but did not establish a completed D1 production integration. | D1 must use real context, Overview, platform-health, and SSE contracts with no fixture production path. |
| D2 evidence | Full composed Explore/Trace read contracts and all provenance joins were not verified as complete. | D2 starts metadata-first and expands only when provenance, freshness, completeness, redaction, and tenant-negative evidence gates pass. |

## Canonical dependency model

Use these graph terms everywhere: **P0**, **P1**, **D0**, **P6-bootstrap**, **P6-slice-certification**, **D1**, **D2**, **D3**, **D4**, **D5**, **D6**, **E1**, **E2**, **E3**, and **E4**. The acyclic dependency model is:

```text
P0 → P1
P0 + P1 → (D0 ∥ P6-bootstrap)
D0 + P0 + P1 + P6-bootstrap → D1
P2 + P6-slice-certification → D2
P3 + P6-slice-certification → D3
P3 + P6-slice-certification → D4
P1 + P2 + P4 + P6-slice-certification → D5
P4 + P6-slice-certification → D6
P6-bootstrap + D1 + D2 evidence → E1
resilience evidence → E2
E1 + E2 → E3
all P/D evidence + E1 + E2 + E3 + full F4 register disposition (including F4-035) → E4
```

`P6-bootstrap` establishes the harness and manifest contract. `P6-slice-certification` is produced separately for each D slice after that slice's required P contract is available; it is not a claim that all assurance work is complete. `D0` and `P6-bootstrap` may proceed in parallel only after P0 and P1 are available. `E1` consumes P6-bootstrap plus D1/D2 evidence, `E2` consumes resilience evidence, `E3` follows E1 and E2, and E4 signs off all evidence and the full F4 register, including F4-035 surface separation.

The graph is a proposed sequencing contract, not a claim that any step is complete.

## Closure rule

A finding reaches **implemented-with-evidence** only when the referenced milestone has a merged implementation and reproducible verification artifact. A finding reaches **residual-risk** only with an accepted residual-risk record, owner, review date, and operational rollback or mitigation decision. A roadmap page alone is evidence of intent, not closure. **Zero open P0 findings** is mandatory for Phase 4 exit (4.E.4).

**Follow-up (F4-028/029/030):** After [#873](https://github.com/Rick1330/ibex-harness/pull/873) merges, update F4-028/029/030 to implemented-with-evidence only when the merged verification artifacts are attached; otherwise retain planned/specification or residual-risk.
