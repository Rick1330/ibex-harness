# Phase 4 — Operator Platform & Multi-Provider

<Callout type="note" title="Roadmap contract">
  This phase is now organized around **capability, assurance, and release gates**. A milestone is not complete because a route, schema, permission bit, or planning document exists. It is complete when its stated contract, verification evidence, and rollback behavior are implemented and recorded.
</Callout>

<Callout type="info" title="Current status">
  **Phase 3.5 is complete and 4.C.5 is treated as complete for planning.** The operator dashboard implementation must begin with Track P. The original Track D feature list is superseded by the redesigned sequence below because its runtime, data, authorization, privacy, and production prerequisites were not sufficiently defined.
</Callout>

## What Phase 4 delivers

Phase 4 turns IBEX from a proxy and API-oriented system into a governed operator platform. It delivers authenticated tenant-scoped management, enforceable rate controls, resilient multi-provider routing, an auditable evidence plane, a world-class operator dashboard, and a release process that proves recovery, security, accessibility, performance, and rollback.

## Critical path

`4.P.0 → 4.P.1 → 4.P.2 → 4.P.3 → 4.P.4/4.P.5/4.P.6 → 4.D.1 → 4.D.2 → 4.D.3/4.D.4 → 4.D.5/4.D.6 → 4.E.1–4.E.4`

Tracks A and B continue independently. Track C provides the completed streaming baseline and must pass its release-evidence checks before realtime dashboard claims are accepted. Track P is the non-negotiable gate before any dashboard UI milestone is marked complete.

## Entry conditions

- Phase 3.5 extraction, context assembly, and MCP memory tools are complete.
- The authenticated API and RLS foundations from Track A are available for extension.
- 4.C.5 streaming hardening is treated as the planning baseline.
- The phase owner has accepted the Track P / Track D redesign and its evidence-based completion model.

## Phase exit conditions

1. Track P gates pass for runtime, identity, evidence, privacy, platform, and assurance.
2. The operator application is deployed on a server-capable topology or a separately deployed SPA/API/SSE topology.
3. A nested multi-step agent run can be queried, explained, redacted, replayed safely, and linked to sessions, memories, tools, policies, evaluations, and incidents.
4. Tenant isolation is demonstrated across synchronous and asynchronous paths.
5. Usage and cost facts reconcile to immutable events and hard caps are enforced by the proxy.
6. Required Playwright, axe, keyboard, contract, load, chaos, recovery, and supply-chain checks pass in the intended environment.
7. Staged rollout, automatic abort, rollback, backup/restore, and residual-risk sign-off are evidenced.
8. The Phase 4 gap register has zero open P0 gaps and all remaining P1/P2 items have owners and dates.

## Findings carried into this phase

The redesign records the following findings as roadmap requirements rather than informal notes:

| Finding | Consequence |
|---|---|
| The current public web deployment is a static documentation site. | Runtime topology and live API/SSE origin are prerequisites. |
| Current trace persistence is an aggregate request row. | Canonical nested trace/span/event evidence must precede Trace Inspector UI. |
| Permission constants are not dashboard contracts. | Versioned API, tenancy, field policy, and step-up authorization are required. |
| ClickHouse TTL is not coordinated deletion. | Retention, tombstones, per-store watermarks, and deletion receipts are required. |
| Usage/cost tables assumed by the old 4.D.5 do not exist at the required scope. | Immutable usage ledger, rate-card versions, reconciliation, and enforcement are required. |
| Deployment, restore, and Playwright gates are described but not wired as acceptance gates. | Track P.5/P.6 and Track E make them executable and required. |
