# Milestone 4.P.4 — Query, Usage & Cost Data Platform

**Status:** Planned  
**Outcome:** Dashboard reads are bounded and explainable, and usage/cost facts can safely drive policy.  
**Track:** [Track P — Operator Readiness, Evidence & Control Plane](/roadmap/phase-4-multi-provider/tracks#track-p--operator-readiness-evidence--control-plane)  
**Dependencies:** Track A identity/API foundations; Phase 3.5; 4.C.5 baseline  
**Estimated effort:** 4 weeks

<Callout type="note" title="Completion contract">
  This milestone is complete only when the implementation, versioned contract, verification evidence, operational signals, and rollback behavior described below are present. A mock screen, planning-only schema, permission constant, or passing unit test alone is not sufficient evidence.
</Callout>

## Why this milestone exists

Dashboard reads are bounded and explainable, and usage/cost facts can safely drive policy.

## Scope and deliverables

Define shared query grammar, facets, autocomplete, URL state, cursor pagination, query budgets, ClickHouse query shapes (every shape requires an explicit org_id parameter and applies an org_id predicate), freshness/completeness fields, immutable usage ledger, rate-card versions, currency, estimated/actual cost, budget periods, alerts, reconciliation, and enforcement decisions.

## Contract and data requirements

Usage facts are keyed by org_id, agent, provider, model, run, time, token class, tool units, latency, status, fallback, rate-card version, and policy version.

## Product and UX requirements

Filters, sort, matched/displayed counts, sampling, retention, freshness, and cost source are visible. High-cardinality IDs remain event fields, not metric labels.

## Non-functional requirements

Filters happen before pagination. Query p95/p99, bounded memory, raw-to-aggregate reconciliation, retry dedupe, and hard-cap negative tests pass.

## Verification gates

Run query contract, EXPLAIN, reconciliation, duplicate-ingestion, fallback-attribution, rate-card replay, and hard-cap enforcement tests.

## Rollout and rollback

Shadow ledger and alert-only first. Enable soft and hard limits per tenant after parity. Preserve immutable facts. **Trigger:** hard-cap false positives/negatives, reconciliation drift, or query SLO breach. **Reversal:** revert failed hard-cap enforcement to alert-only and stop applying deny decisions from the new ledger. **Verify:** alert-only path still emits decisions; immutable facts remain readable; reconcile outstanding deny/allow records before re-enabling hard caps.

## Findings addressed

This milestone addresses the repository and roadmap findings recorded in Track P and the Phase 4 findings register.
