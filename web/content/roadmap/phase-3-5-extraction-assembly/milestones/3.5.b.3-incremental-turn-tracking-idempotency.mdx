## Why This Milestone Exists

3.5.B.2 writes extracted memories over HTTP to services/memory and updates `last_extracted_turn` in a **separate** worker Postgres UPDATE afterward. A worker-local Postgres transaction **cannot** roll back memory rows another service already committed — the original “single `async with db.transaction()`” sketch is architecturally impossible.

Pre-3.5.B.3, `X-Idempotency-Key` was derived from LLM **output** content. Retries with different wording produced different keys and different `content_hash` values, allowing duplicate memories and wasted extraction spend.

This milestone closes that gap with **distributed, input-keyed idempotency** plus ordered pointer updates. Content-hash exact dedup (m3.C.2) remains a complementary backstop, not a substitute.

---

## Non-Goals

- Distributed two-phase commit / outbox between worker and memory service
- Quality evaluation (3.5.B.4)
- Operator-dashboard-visible turn-level status tracking (Phase 4)
- Moving `last_extracted_turn` mutation behind a new memory-service HTTP endpoint
- Changing worker→memory PAT auth

---

## Design (as implemented)

1. **Batch-position idempotency keys** — `X-Idempotency-Key` derived from `(org_id, session_id, batch_fingerprint, turn_index, ordinal)` where `batch_fingerprint` hashes sorted pending turn indexes + input content digests. Does **not** include LLM output text.
2. **Memory HTTP retry semantics** — treat `409 IDEMPOTENCY_CONFLICT` and `409 DUPLICATE_CONTENT` as definitive success (first-commit wording wins); replay and 2xx unchanged.
3. **Ordered pointer update** — `last_extracted_turn` advances only after every write in the batch succeeds; pointer UPDATE failures are retryable via Celery `autoretry_for`.

**Residual limitation (documented, not oversold):** crash after all writes succeed but before pointer UPDATE causes **one additional** `provider.extract` call on retry — bounded, not zero LLM cost. Zero-cost retry would require an outbox design (explicitly deferred).

See [ADR-0065](/docs/adr/0065-extraction-batch-idempotency) for full rationale.

## Success signals

- [x] Crash-injection test: exception after all memory writes, before pointer update — retry produces no duplicate memory slots, pointer advances, **exactly one** additional provider call (not zero, not more than one)
- [x] `extract_session_memories` run twice in immediate succession on the same session → identical final state (pointer unchanged, no extra writes)
- [x] Regression test: old content-derived keys diverge on LLM wording change; new batch-position keys do not
- [x] Partial batch failure: mid-batch 5xx → pointer not advanced; full retry safe for already-committed slots
